## 1. Cache architecture

`clinical_cache.py` provides a bounded, process-local LRU cache for curated `EvidenceBundle` results. The default TTL is 900 seconds (configurable from 60 to 1800); the default capacity is 256 entries (16 to 1024). A SHA-256 key covers only allowlisted, normalized clinical terms, jurisdiction, population, trust/date filters, the embedding configuration key, retrieval limits and the PostgreSQL library revision. It contains no patient identity, raw message, assessment facts or final answer. Each lookup reads the authoritative revision from PostgreSQL; a different revision misses the cache across workers. The retrieval path bypasses cache reads and writes after a clinical mutation in the same transaction, so an uncommitted result cannot enter the shared process cache. Cache exceptions fall through to normal retrieval. Redis is not used or required.

The revision is bumped by statement-level triggers on clinical sources, document versions, evidence chunks and index builds. Activation, supersession, retirement, withdrawal, source review flags and index changes therefore invalidate prior entries. The cache is an acceleration only; PostgreSQL remains the source of truth.

## 2. Database load protections

Existing ACTIVE/approved/licensed-source, jurisdiction, trust, effective-date and matching-embedding-build filters remain in place. Vector and lexical candidate limits default to 12 each, final evidence to five, with a maximum of two chunks per source and checksum deduplication. No ANN index or unbounded new retrieval query was introduced. The cache adds a lightweight revision read even on a hit; this trades one small database read for avoiding embedding and candidate queries. Safe logs record hit/miss/bypass, database latency, vector/lexical candidate counts and final count, without raw patient queries or vectors. The operator update checker reads at most 100 due sources per invocation.

## 3. Freshness policy

The new source metadata includes `freshness_class` (`STABLE`, `STANDARD`, `SENSITIVE`), review interval, update-check frequency/status, last check, response fingerprints and review signal. `clinical_freshness.py` classifies evidence as `CURRENT`, `AGING`, `STALE`, `SUPERSEDED` or `WITHDRAWN` using source type, issuing organization, publication/effective date, replacement signal and topic sensitivity. Age is a review signal, not a declaration of medical falsity; stable background material gets a longer interval. Public-health, medicine safety, recall, outbreak and changing-guidance topics use tighter intervals. Terminal versions remain excluded at the SQL boundary. Stale curated evidence is not allowed to satisfy a time-sensitive request.

## 4. Trusted search and source registry

When explicitly enabled, official-web search is a fallback for missing/insufficient/stale curated evidence and for clearly time-sensitive topics; ordinary well-supported curated questions do not search. `clinical_web.py` now calls the [Tavily Search API](https://docs.tavily.com/documentation/api-reference/endpoint/search) with `search_depth=basic`, `max_results=8`, `include_domains` set to the topic-specific approved subset, and `include_domains_mode=restrict`. Auto-parameter escalation, raw-content and answer generation are off. The Gemini Google Search adapter and `CLINICAL_WEB_SEARCH_MODEL` requirement are removed; Gemini remains the reasoning and embedding provider. The service records provider, invocation outcome, raw result count, accepted/rejected count, latency and failure category without search text.

Tavily's domain restriction is search narrowing, **not** the clinical trust boundary. Every candidate is independently checked for direct HTTPS, exact approved host **and** requested topic subset, with no credentials, port or fragment. Disallowed raw results are discarded and counted; they never reach fetch, reasoning or Sources, and do not invalidate other approved hits. The final HTTP response URL is checked again. The server first fetches bounded HTML/PDF directly from the official host (2 MB maximum, at most five PDF pages extracted), deriving title/date/excerpt there. On eligible disconnect, anti-bot/server error or supported parsing failure only, it may send an already-validated URL to [Tavily Extract](https://docs.tavily.com/documentation/api-reference/endpoint/extract) using `basic` depth and plain-text output. At most two Extract candidates are attempted, and a successful one ends further extraction work. Extract response size and content are bounded, the returned URL must exactly equal the validated request URL, and the body must contain relevant clinical text. Extract-backed title is derived from the validated URL path, organization/jurisdiction from the registry, and date is left unknown; provider-supplied title/date/organization are not accepted. Both paths create backend-generated `EvidenceItem` IDs. The existing evidence-context/citation controls treat page text as data and reject arbitrary model citations. The entire optional web fallback retains a 30-second deadline; failures return control to cautious ungrounded AI. Incomplete direct content is never accepted.

The initial exact-host registry covers Nigeria's Federal Ministry of Health and Social Welfare (`health.gov.ng`), NCDC (`ncdc.gov.ng`) and NAFDAC (`nafdac.gov.ng`), plus WHO (`who.int`, `www.who.int`, `iris.who.int`), FDA (`www.fda.gov`), EMA (`www.ema.europa.eu`) and NICE (`www.nice.org.uk`). The approved `www` aliases are treated as the same authority, not a new publisher. Topic selection prefers NAFDAC alone for Nigeria drug recalls, NCDC/FMOH for Nigeria outbreaks, and WHO/NICE/FMOH as appropriate for other guidance. New hosts require clinical/governance review. The registry is an authority allowlist, not approval of every page on those hosts. Official-domain identity was checked against [Nigeria FMOH](https://health.gov.ng/), [NCDC](https://www.ncdc.gov.ng/ncdc), [NAFDAC](https://nafdac.gov.ng/), [WHO](https://www.who.int/about-us), [FDA](https://www.fda.gov/) and [EMA](https://www.ema.europa.eu/en/about-us).

## 5. Privacy and medicine safety

Conversation and assessment text is reduced to allowlisted clinical concepts before embedding or search; names, addresses and the raw chat never cross the search boundary. Only a clinical jurisdiction code is included where applicable. Medicine recall, warnings, contraindication, approval and similar current-safety concepts trigger the freshness path even if curated evidence exists. If a validated, newer official page from the same issuing organization is found, it precedes/replaces the older curated item for that answer and best-effort flags the curated source `UPDATE_AVAILABLE` for human review. Old versions are not deleted or automatically replaced in the library. No current official result means no claim that current guidance was verified.

## 6. Source update checking

`clinical_source_updates.py` checks ACTIVE sources' approved canonical URLs within a configured frequency and bounded batch. It records baseline/unchanged fingerprints, or marks content changes, a changed canonical URL, a redirect, or a missing page for review; network failures are reported separately. It never follows a redirect to ingest content and never auto-activates a replacement. The existing backend APScheduler now runs due checks **daily at 03:15 UTC**; a PostgreSQL transaction advisory lock prevents concurrent Render workers from duplicating the batch. An optional `POST /api/v1/internal/clinical/source-updates/check` trigger requires a 32+-character `X-Clinical-Worker-Token` matching `CLINICAL_SOURCE_UPDATE_WORKER_TOKEN`, and fails closed when unset. No paid worker/cron infrastructure is required. `backend/app/tools/clinical_knowledge_cli.py check-updates` and `updates-report` remain manual operator commands. An initial baseline proves only what the remote page returned on that check; it does not prove the ingested edition matches that page. Operators must review and approve any update. The scheduled path is code- and test-verified, but its deployed MDQ service operation was not observable here.

## 7. Failure behavior and Flutter

Cache error means database retrieval. Database/embedding error means an empty curated bundle and, if separately enabled, an attempt at official-web fallback. Search/fetch error means no web evidence; the existing cautious ungrounded Conversation/Assessment paths remain available. PostgreSQL retrieval uses a SAVEPOINT so a failed lookup does not roll back the outer chat/assessment transaction. Citation IDs are checked against backend-created items and provider-supplied URLs are rejected. The existing Flutter Sources control renders only referenced server-validated title, organization, useful section/page/date and optional HTTPS link; no cache state, score or internal freshness code is displayed. No Flutter source change was needed for Wave 5.
